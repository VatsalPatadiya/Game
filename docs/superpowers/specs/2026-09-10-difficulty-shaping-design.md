# Difficulty-Shaping Layer for Board Generation — Design

**Date:** 2026-09-10
**Status:** Approved approach (Approach 1), spec under review
**Scope:** Add a controllable difficulty layer on top of the existing solvable-board
generator, so that matches are *easy to identify* early (in a board and in early
levels) and get *progressively harder* — driven by two levers: **branching factor**
(how many valid matches are available at once) and **visual confusability** (how many
look-alike symbols share the board). Supports both **pair-match** and **triple-match**.

---

## 1. Background & Problem

The game is a **tray-collection mahjong-solitaire**:

- Tap a *free* tile → it flies into a tray (capacity `BoardState.MaxTraySize`, currently 4).
- When 2 identical tiles (pair mode) or 3 identical (triple mode) collect in the tray,
  they auto-clear.
- If the tray fills with all-distinct tiles (no completable set), it's **game over**.

Boards are generated by **reverse construction** (`ReverseConstructionSolver` +
`BoardGenerator`):

- Repeatedly pick a group of currently-*free* slots (2 for pairs, 3 for triples) and
  record them as a removal step; assign each recorded group one shared value.
- Because every group was simultaneously free, *following that order taps a completable
  set back-to-back and clears it without ever exceeding the tray* — so **every generated
  board is guaranteed solvable and tray-safe**. (`FreedomRuleCalculator.IsFree`: a slot
  is free when nothing covers it and its left OR right same-layer neighbor is empty.)

**What's missing:** difficulty is *uncontrolled*. `TurtleShapeBuilder.BuildForDifficulty`
scales board *shape/size* per level, but value assignment
(`AssignValuesFromRemovalOrder`) shuffles values **completely at random**. So there is no
guarantee that a board's *opening* is easy to read, nor a designed curve from
easy → hard. A random shuffle can produce a level-1 board whose only valid opening match
is buried, or a board where every free tile is a distinct value (high tray-overflow risk).

**Goal:** make difficulty an explicit, verified property of a generated board, on **two
axes** (across levels *and* within a single board) using **two levers** (branching factor
+ visual confusability), *without* weakening the solvability/tray-safety guarantee.

---

## 2. Non-Goals (YAGNI)

- Not changing solvability/tray-safety — reverse construction stays the source of truth.
- Not adding proximity-based or type-count-based difficulty (explicitly deprioritized by
  the design owner).
- Not authoring per-level hand-made layouts (that was Approach 3, rejected).
- Not reworking board *shapes*; `TurtleShapeBuilder` stays as-is. We shape **values and
  symbols**, not geometry.

---

## 3. Key Concepts

### 3.1 Branching factor B(t)

At any point *t* during a forward solve, define **B(t) = the number of distinct values
that currently have a *completable set of free copies*** — i.e. for pairs, values with ≥2
free copies; for triples, values with ≥3 free copies. Intuitively: *how many different
"obvious" matches can the player make right now without parking a tile in the tray and
searching.*

- **High B(t) = easy:** many independent matches available; the player can almost always
  tap two/three tiles that clear immediately, so the tray stays near-empty.
- **Low B(t) (→1) = hard:** often only one completable set exists among free tiles; the
  player must tap distractor tiles into the tray while hunting, risking overflow.

The **branching profile** is the curve of B over the solve, sampled as *fraction of tiles
remaining* on the x-axis. We target a curve that starts **high** and **descends** toward
the end. Note the tail is naturally low (few tiles left), so the meaningful control is the
**opening and early-mid game**.

### 3.2 Visual confusability

Each symbol belongs to a **similarity cluster** (authored, see §5.2): e.g.
`round-red = {apple, tomato, cherries}`, `round-orange = {orange, lemon}`,
`green-veg = {broccoli, avocado}`. A board's **confusability level** = how many symbols
drawn from the *same* cluster appear on the board at once.

- **Distinct palette (easy):** at most one symbol per cluster → nothing looks alike.
- **Confusable palette (hard):** multiple symbols from the same cluster are present, so
  the player must look carefully to tell a match from a near-match.

## 4. Architecture

New/changed pieces (all in `GameDomain.Generation` + `GameClient.Data`, matching existing
namespaces and the Domain/Presentation split):

```
LevelData.Difficulty (1..5)  ─┐
                              ├─►  DifficultyProfile.For(difficulty)   [NEW]
                              │        · MatchMode (Pair|Triple)
                              │        · BranchingTarget curve (high→low knobs)
                              │        · ConfusabilityLevel (0..N)
                              ▼
        BoardGenerator.Generate / GenerateTriples(level, rng, profile)   [CHANGED]
          1. ReverseConstructionSolver.TryBuildRemovalOrder(...)         (unchanged: solvable order)
          2. ValueAssigner.Assign(order, profile, rng)                   [NEW] — shapes branching
          3. BranchingSimulator.Profile(board, slotsById, matchMode)     [NEW] — measures B(t)
          4. if !profile.Accepts(measuredCurve) → reseed (existing retry loop)
          5. PaletteSelector.Select(profile, tileSet, distinctValueCount) [NEW] — maps values→symbols
                              ▼
                    BoardState (values already mapped to chosen symbols)
```

- **`DifficultyProfile`** (new, `GameDomain.Generation`): pure data + a `For(int
  difficulty)` factory and an `Accepts(branchingCurve)` predicate. This is the single
  place difficulty is *defined*, so tuning lives in one file.
- **`ValueAssigner`** (new): replaces the branching-agnostic
  `AssignValuesFromRemovalOrder*` methods with a profile-aware assigner (old methods kept
  as the `ConfusabilityLevel=0`, flat-branching default for back-compat + existing tests).
- **`BranchingSimulator`** (new): given a board + shape + match mode, plays a *greedy
  reference solve* and records B(t). Pure/deterministic, no Unity deps → unit-testable.
- **`PaletteSelector`** (new): maps the abstract values (`"0".."25"`) the assigner
  produced onto concrete symbol indices from the tile set, honoring the confusability
  level. Kept separate from branching so the two levers compose independently.
- **`TileSetAsset`** (changed, `GameClient.Data`): add `int[] SimilarityClusterId` (one
  per icon) so the generator knows which symbols look alike.

**Why this decomposition:** branching (value *grouping*) and confusability (value→*symbol*
mapping) are independent concerns — one is about *when* matches are available, the other
about *how they look*. Splitting `ValueAssigner` and `PaletteSelector` lets each be
understood and tested alone, and lets a board be "easy branching / hard visuals" or any
combination. `BranchingSimulator` is isolated because it's the verification oracle and
must stay dependency-free to run in EditMode tests.

## 5. Component Detail

### 5.1 DifficultyProfile

```csharp
public enum MatchMode { Pair, Triple }

public sealed class DifficultyProfile
{
    public MatchMode Mode;
    // Branching curve knobs (fraction-of-tiles-remaining → target B):
    public float OpeningBranchingMin;   // e.g. easy=6, hard=2  (min completable sets at start)
    public float EndgameBranchingMin;   // e.g. easy=2, hard=1
    public float BranchingTolerance;    // how far below target we still accept
    public int   ConfusabilityLevel;    // 0 = one symbol/cluster; N = up to N+1 per cluster
    public int   DistinctValueCount;    // symbol variety on the board (secondary knob)

    public static DifficultyProfile For(int difficulty, MatchMode mode); // 1..5 → tuned presets
    public bool Accepts(IReadOnlyList<int> measuredBranchingByStep);      // curve within tolerance?
}
```

`For` returns tuned presets. Illustrative starting table (final numbers tuned during
implementation against real boards):

| Difficulty | OpeningBranchingMin | EndgameBranchingMin | ConfusabilityLevel | Feel |
|---|---|---|---|---|
| 1 | 6 | 2 | 0 | Openings flush with obvious matches; all symbols distinct |
| 2 | 5 | 2 | 0 | Still generous; distinct symbols |
| 3 | 4 | 1 | 1 | Some look-alikes introduced |
| 4 | 3 | 1 | 2 | Tighter matches + more look-alikes |
| 5 | 2 | 1 | 3 | Frequently a single valid match; heavy look-alikes |

`Accepts` checks the *early* portion of the measured curve (say first 40% of steps) meets
`OpeningBranchingMin - BranchingTolerance`, and the curve is **non-increasing in trend**
(monotone-ish, allowing small noise) toward `EndgameBranchingMin`. This is what encodes
"first few pairs easy, then level up."

### 5.2 TileSetAsset similarity clusters

Add `public int[] SimilarityClusterId;` (parallel to `Icons`). Authored by hand in the
Inspector for the ~26 food symbols. Value `-1` = "unique, in no cluster." A tiny EditMode
test asserts the array length matches `Icons.Length` so it can't silently drift.

### 5.3 ValueAssigner — branching-shaped assignment (PAIR)

Input: the removal order `List<(a,b)>` from `ReverseConstructionSolver` (already
tray-safe), the profile, and rng. Output: `Dictionary<slotId,value>`.

Core idea — **branching = number of pairs whose *both* tiles are free at a given state.**
The removal order already tells us, step by step, which slots are free. To get **high
opening branching**, we assign *distinct* values to many pairs that are *co-free early*
(so several completable pairs exist at once). To **taper**, we let later pairs share the
value-availability window with fewer siblings.

Algorithm (deterministic given rng):

1. Reconstruct, from the removal order, each slot's **freed-at step** `f(slot)` (the step
   at which it first became free during reverse construction).
2. Group the ordered pairs into **branching bands** by target: the first band (opening)
   gets enough *distinct* values that ≥ `OpeningBranchingMin` pairs are co-free; later
   bands progressively **reuse the value pool later / interleave** so fewer pairs are
   simultaneously completable, walking down toward `EndgameBranchingMin`.
3. Assign values band-by-band, shuffling within a band (rng) so boards still vary.
4. This never violates tray-safety: values still come in exact pairs mapped onto the
   solvable removal order; we only choose *which* pair gets *which* value.

If the assigner cannot hit the opening target for a given shape (e.g. a very deep,
narrow board has too few co-free slots early), it returns a best-effort assignment and
lets `BranchingSimulator` + `Accepts` decide; failing that, the generator reseeds.

### 5.4 ValueAssigner — TRIPLE

Identical shape, but the unit is a group of 3 (from `TryBuildRemovalOrderTriples`) and
B(t) counts values with ≥3 free copies. Tray capacity 4 ≥ 3, so a co-free triple always
clears without overflow (the existing triple builder already guarantees 3-free groups).
Confusability interacts more strongly here (3 look-alikes on screen), so triple presets
use a **lower** `ConfusabilityLevel` than pair presets at the same difficulty.

### 5.5 BranchingSimulator — the verification oracle

```csharp
public static List<int> Profile(BoardState board,
                                Dictionary<string,TileSlot> slotsById,
                                MatchMode mode);
```

Plays a **greedy reference solve** on a *copy* of the board: at each step compute free
slots (reuse `FreedomRuleCalculator.ComputeFreeSlots`), count B (values with ≥2 / ≥3 free
copies), record it, then clear one completable set (prefer keeping options open) and
repeat until solved or stuck. Returns B per step. Deterministic, no Unity types →
EditMode-testable. Used both by the generator (accept/reject) and by tests.

> Note: the greedy reference solve measures *available* branching, i.e. an upper-ish bound
> on how easy it is to find a match. It is a heuristic proxy, not the player's exact path,
> which is the right granularity for a difficulty knob.

### 5.6 PaletteSelector — value → symbol mapping (confusability)

Input: the set of abstract values used on the board, the tile set (with cluster ids), and
the profile. Output: a mapping `value → iconIndex`.

- **ConfusabilityLevel = 0:** choose symbols so every value maps to a symbol from a
  *distinct* cluster (or a unique symbol). Nothing on the board looks alike.
- **ConfusabilityLevel = k:** deliberately allow up to `k+1` values to map to symbols from
  the *same* cluster, choosing clusters with enough members. This forces look-alikes onto
  the board.
- Respects `DistinctValueCount` and never maps two *different* values to the *same* icon
  (that would break matching). If the tile set lacks enough symbols/clusters for the
  requested level, it clamps to the max achievable and logs a warning (see §6).

## 6. Data Flow & Error Handling

1. `GameController.LoadLevel` builds shape (unchanged) and now also
   `DifficultyProfile.For(difficulty, mode)` where `mode` comes from level config
   (pair vs triple — see §8 open item).
2. `BoardGenerator.Generate*(level, rng, profile)`:
   - Build removal order (existing). If null → reseed (existing behavior).
   - `ValueAssigner.Assign(order, profile, rng)`.
   - `BranchingSimulator.Profile(...)`; if `!profile.Accepts(curve)` → **reseed** (same
     `maxRestarts` loop, bumped from 50 → 200 since we now reject on two criteria).
   - `PaletteSelector.Select(...)` maps values→icons; store icon index in `TileCell`
     (or keep value + resolve at render — see §8).
   - If after `maxRestarts` no board satisfies the profile, **fall back to the flat
     (random) assignment** and log a warning rather than throw — a slightly-off-difficulty
     but solvable board beats no board. (`BoardGenerationException` is still thrown only if
     no *solvable* order exists at all, preserving current contract.)
3. Palette/cluster shortfalls **degrade gracefully** (clamp + warn), never throw.

**Guiding principle:** solvability is a *hard* invariant (throw if violated); difficulty
is a *soft* target (reseed, then fall back + warn).

## 7. Testing Plan

New EditMode tests (alongside existing `Generation/` and `Regression/` suites):

1. **`BranchingSimulatorTests`** — hand-built small boards with known B(t); assert the
   simulator reports the expected curve for pair and triple.
2. **`ValueAssignerTests`** — assigned boards remain solvable/tray-safe (cross-check via
   existing `ReverseConstructionSolver`/greedy solve); opening branching ≥ target for
   easy profiles; curve trends non-increasing.
3. **`PaletteSelectorTests`** — level 0 confusability ⇒ no two on-board symbols share a
   cluster; level k ⇒ at least one same-cluster pair present when the tile set allows;
   never two values → same icon.
4. **`DifficultyProfileTests`** — `Accepts` correctly passes/fails representative curves;
   presets are monotone (higher difficulty ⇒ lower opening branching / higher
   confusability).
5. **Extend `SolvabilityRegressionTests`** — every difficulty 1..5, both modes, N seeds:
   still 100% solvable AND passes its own `Accepts`. This is the guard that difficulty
   shaping never breaks beatability.
6. **`TileSetAsset` cluster-length test** — `SimilarityClusterId.Length == Icons.Length`.

Follows the repo's existing pattern (pure domain logic, no Unity runtime needed).

## 8. Open Items to Resolve During Implementation

- **Pair vs triple selection per level:** today `GameController` always calls
  `Generate` (pair). Add `MatchMode` to `LevelData` (default Pair) so a level can opt into
  triples; wire `GenerateTriples` accordingly. (Small, mechanical.)
- **Store icon index vs. value:** decide whether `PaletteSelector` writes the resolved
  icon index into `TileCell` or whether rendering resolves `value → icon` via a per-board
  map. Prefer a **per-board value→icon map on `BoardState`** to keep `TileCell.Value`
  as the match key (matching logic in `MatchValidator`/tray stays untouched).
- **Preset tuning:** the §5.1 table numbers are starting points; final values tuned by
  running `BranchingSimulator` over generated boards and eyeballing on-device.

---

## 9. Summary

A thin, well-isolated difficulty layer sits on top of the untouched solvable-board
generator. `DifficultyProfile` defines the curve; `ValueAssigner` shapes *when* matches
are available (branching, easy→hard within a board and across levels); `PaletteSelector`
shapes *how alike* they look (confusability); `BranchingSimulator` verifies the result and
the generator reseeds until both solvability (hard) and the difficulty target (soft) hold.
Both pair and triple modes are supported. No existing gameplay, matching, or tray code
changes semantically.
